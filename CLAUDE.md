# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `docker compose up -d redis` — this project's own Redis (`messenger_redis`, `127.0.0.1:${REDIS_PORT}`, password `REDIS_PASSWORD` from `.env`); needed before `npm run dev` whenever `REDIS_HOST` / `REDIS_URL` is set, since the server exits if Redis is unreachable at boot. In compose the `app` service reaches it as `redis:6379` (compose overrides `REDIS_HOST` / `REDIS_PORT` and clears `REDIS_URL`)
- `npm run dev` — runs the custom server (`tsx watch server.ts`): Next dev (Turbopack) + socket.io on http://localhost:3000. `next dev` alone has no realtime. Code under `app/` hot-reloads through Next; `tsx watch` restarts the whole process when a file it loaded itself changes (`server.ts`, `server/`, the `app/libs` files the socket server imports, `next.config.js`). It ignores dot folders (so `.next` chunks never trigger a restart) and `node_modules`; `.env` changes still need a manual restart.
- `npm run build` / `npm start` — production build (Turbopack) / serve (`start` also goes through `server.ts`)
- `npm run lint` — ESLint 9 CLI (`eslint .`) with `eslint.config.mjs`, which spreads `eslint-config-next/core-web-vitals` (native flat config, includes the React Compiler hook rules); covers `server.ts` and `server/` too
- `npm test` — Vitest (`vitest run`); `npx vitest run tests/api/routes.test.ts -t "DELETE"` runs one file / matching tests; `npm run test:watch` to watch
- `npx tsc --noEmit` — typecheck
- `npx prisma db push` — sync `prisma/schema.prisma` to MongoDB, including its `@@index`es (no migrations; MongoDB provider)
- `npx prisma generate` — regenerate the client (also runs on `postinstall`)

Tests live in `tests/`: `unit/` (libs, `proxy.ts`, message-file parity and the theme init script), `api/` (route handlers called directly, with Prisma, `getCurrentUser`, socket emits and S3 calls mocked; `tests/helpers.ts` has the Prisma mock and fixtures), `socket/` (a real socket.io server from `initSocketServer` on a random port, real `socket.io-client`s; only `getToken` and Prisma are mocked). Tests needing Redis are skipped unless `TEST_REDIS_URL` is set: `docker run --rm -p 6390:6379 redis:7-alpine`, then `TEST_REDIS_URL=redis://localhost:6390 npm test`. Test env vars (fake AWS, bucket) are in `vitest.config.mts`, which also inlines `next-intl` (its ESM imports `next/server` without an extension, which Node can't resolve). Open the workspace as `E:\gitlab\Messenger`: Vitest 5 fails every file with "Cannot read properties of undefined (reading 'config')" when the shell reports the drive as `e:\` instead of `E:\` (Linux/CI are unaffected).

Both `package-lock.json` and `yarn.lock` are committed (npm keeps both in sync).

CI/CD (`.gitlab-ci.yml`, same model as the portfolio repos): a shell runner tagged `main` on the production server runs every job in throwaway Docker containers (checkout mounted read-only and copied, `node:22` Debian because Prisma needs OpenSSL). On every MR and `main`: `lint` (`tsc` + ESLint), `test` (Vitest with a per-job Redis container on a private network, so the Redis tests run), `audit` (osv-scanner on `package-lock.json`, never blocks; accepted advisories with an expiry in `osv-scanner.toml`). On `main` only: `build` (`scripts/ci-docker-build.sh` builds the `Dockerfile` image tagged `<project>:<sha>`, passing `AWS_REGION` / `AWS_S3_BUCKET` / `NEXT_PUBLIC_S3_PUBLIC_URL` as build args because `next.config.js` reads them at build time) and `deploy` (`prisma db push` from the new image, then `docker compose up`; keeps the last 5 images for GitLab's "Rollback environment"). The production `.env` comes from the File-type CI/CD variable `ENV_FILE`. The Dockerfile's `HEALTHCHECK` calls `GET /api/health` (database ping + socket.io running; 200 / 503); `deploy` waits for `healthy` and otherwise prints the logs, starts the previous image again and fails. Security headers (enforced `frame-ancestors` / `object-src` / `base-uri` CSP, a full CSP as Report-Only until Next's inline scripts get nonces, `Permissions-Policy` for camera / mic, HSTS in production) are set in `next.config.js`; new external hosts (images, uploads, CDNs) go into its CSP lists too. The image runs `server.ts` through tsx (no `standalone` output, since the custom server needs the source), so `prisma` is a dependency, not a devDependency.

`npm run dev` and `npm start` share `.next/`, so run `npm run build` again after a dev session before `npm start`.

Copy `.env.example` to `.env`: `DATABASE_URL` (MongoDB), `NEXTAUTH_SECRET`, AWS (`AWS_REGION`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_S3_BUCKET`, optional `NEXT_PUBLIC_S3_PUBLIC_URL`), GitHub and Google OAuth credentials. Optional: Redis for several instances, either `REDIS_URL` or `REDIS_HOST` / `REDIS_PORT` / `REDIS_PASSWORD` (`getRedisUrl()` in `app/libs/redis-url.ts`; `REDIS_URL` wins), `TURN_URLS` / `TURN_SECRET` / `TURN_TTL_SECONDS` (TURN for calls), `TRUST_PROXY=true` (behind a proxy that sets `X-Real-IP`), `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_SUBJECT` (Web Push; `npx web-push generate-vapid-keys`, read at run time, keep the pair stable).

## Architecture

Next.js 16 App Router messenger app (React 19), TypeScript, Tailwind 3, Prisma 6 + MongoDB, NextAuth v4, socket.io for realtime, WebRTC for 1:1 video calls, S3 for uploads. UI strings are partly in Vietnamese. Path alias `@/*` maps to the repo root.

**i18n (next-intl, same setup as the portfolio CMS)**
- Locales `vi` (default) and `en`; URLs are always prefixed (`/vi/conversations`). `i18n/routing.ts`, `i18n/request.ts` (loads `i18n/messages/<locale>.json`), `i18n/navigation.ts`. Every page lives under `app/[locale]/`, whose `layout.tsx` is the root layout (`<html lang>`, providers). `app/api` and the shared folders (`components`, `hooks`, `libs`, `actions`…) stay outside `[locale]`.
- **Every visible string goes through `t()`** and into both `vi.json` and `en.json` (same keys, same ICU placeholders — `tests/unit/i18n-theme.test.ts` enforces it; plurals as `{count, plural, one {# member} other {# members}}`). `global.d.ts` types `t()` keys from `vi.json`, so a missing key fails `tsc`. Client: `useTranslations("ns")`; server: `getTranslations`. Libs return codes, not text (`validatePassword` → `auth.password_rules.<code>`, `UploadError.code` → `upload.<code>`).
- **Navigation:** use `Link`, `useRouter`, `usePathname`, `redirect` from `@/i18n/navigation`, never `next/link` / `next/navigation` (they drop the locale). `usePathname()` returns the path without the locale. `useParams` from `next/navigation` is fine.
- Dates: `format(date, "p", { locale: useDateLocale() })` (`app/hooks/useDateLocale.ts`).
- `proxy.ts` runs the next-intl middleware and, for `/conversations`, `/users`, `/room`, checks the NextAuth JWT (`getToken`) and redirects signed-out users to `/<locale>` (the login page). Its matcher skips `api`, `socket.io`, `_next` and files.
- The language is switched by `LanguageToggle` (sidebar, mobile footer, login page) and in the settings modal; next-intl remembers it in the `NEXT_LOCALE` cookie.

**Theme (dark mode, same provider as the portfolio FE/CMS)**
- `app/components/providers/ThemeProvider.tsx`: `light` / `dark` / `system` (default), stored in `localStorage.theme`, applied as the `dark` class on `<html>` (Tailwind `darkMode: "class"`). `THEME_INIT_SCRIPT` runs in `<head>` before paint so dark users get no light flash — keep it in the `[locale]` layout. `ThemeToggle` flips light/dark; the settings modal offers all three.
- Colors are tokens (CSS variables in `app/globals.css`, light in `:root`, dark in `.dark`; wired in `tailwind.config.js`): `bg-background`, `bg-muted`, `text-foreground`, `text-muted-foreground`, `border-border` (also the default for plain `border`), `ring-input`. **Use tokens, not raw grays/white/black**, so both themes work; brand colors (sky, rose, green, purple) are fine. The call screen (`app/[locale]/room`) is always dark (video) and keeps raw colors. react-select (`Select.tsx`) and toasts (`ToasterContext`) are themed explicitly.

Next 15/16 rules that bite here: `params` in pages and route handlers is a `Promise` (`const { id } = await params`); route files may only export handlers/config, so shared values such as `authOptions` live in `app/libs/`; route protection is `proxy.ts` (Next 16's name for middleware); `useRef` needs an initial value under React 19 types; with react-hook-form use `useWatch({ control, name })`, not `watch()` (the React Compiler lint rule flags it).

**Data flow**
- Server components fetch data via functions in `app/actions/` (e.g. `getCurrentUser`, `getConversations`, `getMessages`) that call Prisma directly — plain async server functions, not Server Actions. `getSession` / `getCurrentUser` are wrapped in React `cache()`, so call them freely within a request.
- **Membership rule:** anything keyed by a conversation id (pages, `/api/messages`, `seen`, the messages page API, DELETE) must go through `getConversationForUser(id, userId)`, which returns null for "missing" and "not a member" alike. The socket server does its own check for `conversation:join` / `call:join`.
- **Passwords:** `app/libs/prismadb.ts` sets a global `omit: { user: { hashedPassword: true } }` (Prisma 6), so user rows are safe to pass to client components and sockets. Only the credentials `authorize` in `app/libs/auth.ts` opts back in. Client code types users as `SafeUser` (`app/types`), not Prisma's `User`. Password rules live in `app/libs/password.ts` and run on both the form and `/api/register`.
- Conversation lists load only the last message (`take: 1`); keep it that way when changing `getConversations`. Each item also carries `unreadCount` (`findConversationsForUser`): "seen" marks only the last message, so the newest message the user has seen is the read marker, and only conversations whose last message is unread get a scan of their newest `UNREAD_SCAN_LIMIT` messages (`countUnread`, `app/libs/unread.ts`). `ConversationList` keeps it live (a new message from someone else +1 unless that chat is open and visible; a seen / own last message → 0), shows the "(N) Messenger" tab title and filters by name (`matchesSearch`, `app/libs/search.ts`: case and Vietnamese diacritics ignored; the contacts list uses it too).
- **Sending is optimistic** through the zustand outbox (`app/hooks/useOutbox.ts`): `Form` adds an entry (sending → sent / failed with retry / discard), `Body` renders entries after the list and drops one once its message is in the list, matched by id or by the `clientId` that `/api/messages` echoes in `messages:new` only (never stored). The composer is a textarea (`MessageInput`: Enter sends, Shift+Enter new line, Enter while an IME composes doesn't send); pasting an image uploads and sends it.
- Chat layout: `Body` puts a day divider (today / yesterday / date) where the day changes and groups consecutive messages of one sender within `GROUP_WINDOW_MS` under one header (`app/libs/message-groups.ts`; calls never group). `MessageBox` makes http(s) links clickable (`splitLinks`, `app/libs/linkify.ts`; `target="_blank" rel="noopener noreferrer nofollow"`).
- Reply / edit / recall: `Message.replyToId` (self-relation, `NoAction`), `editedAt`, `deletedAt`. `POST /api/messages` takes `replyToId` (same conversation, not recalled: `NOT_RECALLED`, which also matches documents without the field). `PATCH /api/messages/[messageId]` `{ message }` edits (sender, text, within `EDIT_WINDOW_MS`); `DELETE` recalls (sender, not a call; clears body / image / reactions, keeps the row, cleans the S3 image). Rules in `app/libs/message-actions.ts`, shared with `MessageBox`'s actions. Both emit `messages:update` and, for the last message, `conversation:update` without `lastMessageAt`; `Body` also patches the quotes (`replyTo`, `REPLY_PREVIEW_SELECT`) of replies to it. Reacting to a recalled message is a 400. The composer's mode (reply / edit) is the zustand `useComposer`; Esc cancels.
- Typing: `Form` emits `typing` (conversationId, true) at most every 3 s while writing and `false` on send / blur / empty / leaving; the server relays it to the conversation room only from sockets in it (one "true" per second per socket); `Body` shows "X is typing" (names from the `members` prop) and drops entries after 5 s without a refresh.
- Desktop notifications for new messages (not calls), turned on in the settings modal or the inbox's `NotificationPrompt` (shown while the browser hasn't been asked; "Not now" is remembered); `app/libs/notifications.ts` holds the choice (browser permission + `localStorage.notifications`).
  - **Web Push** (works with every tab closed) when `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` are set: `app/libs/push-client.ts` registers `public/sw.js` and posts the subscription to `/api/push` on every load while on (model `WebPushSubscription`, one per endpoint, with the locale it is written in; at most 10 per user; signing out and turning off delete it). `/api/messages` calls `pushNewMessage` (`app/libs/message-push.ts`, text through `createTranslator` per subscription locale) in the background; `sendPush` (`app/libs/web-push.ts`) never throws and deletes subscriptions answered 404 / 410. Endpoints must be a known push service host (`isPushEndpoint`): the server POSTs to them, so anything else would be SSRF. `sw.js` skips the notification while a window of the app is focused, and a click focuses an open tab and asks it (`postMessage`) to navigate.
  - Without push (not configured / unsupported / not yet subscribed), `MessageNotifications` (in the `[locale]` layout) shows them from the tab while the window isn't focused (`document.hasFocus()`, not only hidden). Both use the tag `conversation-<id>`, so a conversation shows one notification. `/api/messages` sends `name` / `isGroup` in `conversation:update` for its title.
- Messages are paginated: `getMessages(id, before?)` returns 50 at a time (oldest first) plus `hasMore`; the page loads the latest page and `Body.tsx` fetches older ones from `GET /api/conversations/[id]/messages?before=<messageId>` when scrolled near the top.
- **Socket reconnects lose events**, so every `connect` resyncs: `Body.tsx` fetches `?after=<last message id>` (`getMessagesAfter`; more than a page missed → reloads the latest page), `ConversationList` reloads `GET /api/conversations`. `Body.tsx` posts `seen` only while `document.visibilityState === "visible"` (and again when the tab shows), follows new messages down only when near the bottom (or for one's own), else shows a "N new messages" button.
- Emoji: `EmojiPicker` (`app/components`, `emoji-picker-react` loaded with `next/dynamic` on first open; Vietnamese dataset for `vi`, labels through `t()`, theme from `useTheme().resolvedTheme`) inserts at the caret in the composer (`Form.tsx`); with an empty input the send button sends `QUICK_EMOJI` (👍). Emoji are plain text in `body`. `MessageBox` shows a body of 1–`JUMBO_EMOJI_MAX` emoji large without a bubble (`countEmojiOnly`, `app/libs/emoji.ts`; `Intl.Segmenter` graphemes, so flags / families / skin tones count as one).
- Reactions: model `Reaction` (one per user per message, `@@unique([messageId, userId])`, so run `prisma db push` for the index; cascades with the message). `POST /api/messages/[messageId]/reactions` `{ emoji }` (exactly one emoji, `countEmojiOnly`; membership via the message's conversation; `reaction` rate limit) toggles: same emoji removes, another replaces; then emits the reloaded message as `messages:update`. **Every message sent to the chat view uses `MESSAGE_INCLUDE` (`app/libs/message-include.ts`)**: `getMessages`, `/api/messages`, `seen`, the reaction route and `server/call-log.ts`; a `messages:update` replaces the message on the client, so one without `reactions` would wipe them. UI in `MessageReactions.tsx`: `ReactionPicker` (hover smiley, 6 quick reactions + the full `EmojiPickerPanel`) and `ReactionChips` under the bubble.
- Groups: `Conversation.ownerId` (the creator) is the only member who may delete a group (`canDeleteConversation` in `app/libs/conversation-permissions.ts`, used by the route and `ProfileDrawer`); groups from before it have no owner and any member may delete them. Others leave instead: `POST /api/conversations/[id]/leave` disconnects the caller, hands `ownerId` on when the owner leaves, emits `conversation:remove` to the leaver and `conversation:update` with `users` / `userIds` / `ownerId` to the rest (the open chat then `router.refresh()`es); the last member leaving deletes the group. Leaving or deleting also takes the members' sockets out of the conversation room (`removeUserFromConversationRoom`).
- Deleting a conversation (`DELETE /api/conversations/[id]`, `deleteConversation` in `app/libs/conversation-delete.ts`) disconnects the members in the same transaction (`users: { set: [] }`, so `User.conversationIds` is updated — MongoDB many-to-many is not cleaned by a delete), then in the background pulls the deleted message ids from members' `User.seenMessageIds` (`$runCommandRaw` `$pull`) and removes unreferenced images from S3.
- **Rate limits** (`app/libs/rate-limit.ts`, async): register per IP, credentials login per IP and per IP+email (inside `authorize`, error code in `app/libs/auth-errors.ts`), messages, reactions, uploads, new chats, settings, `seen` and push subscriptions per user; limits in `LIMITS`. Counters are in Redis when Redis is configured (`getRedisUrl()`), else in memory; requests never wait for Redis (only a ready client is used, commands time out after 500 ms) and fall back to memory. The IP comes from the `x-client-ip` header that `server.ts` sets from the socket (or from `X-Real-IP` when `TRUST_PROXY=true`); never key on `X-Forwarded-For`.
- Mutations go through Route Handlers in `app/api/**/route.ts`, called from client components with `axios`. After writing to the DB, each handler emits over socket.io via `emitToUser` / `emitToConversation` (`app/libs/socket-server.ts`).
- Server components pass Prisma objects (with `Date` fields) straight to client components; React 19's RSC serialization handles `Date`. Data arriving over socket.io is plain JSON, so dates there are ISO strings.
- `app/libs/prismadb.ts` holds a global Prisma singleton (shared by Next and the socket server).

**Auth**
- `authOptions` lives in `app/libs/auth.ts` (GitHub, Google, Credentials with bcrypt; JWT sessions; Prisma adapter, cast because its types predate Prisma's `omit`); `app/api/auth/[...nextauth]/route.ts` only wraps it. `bcrypt` is listed in `serverExternalPackages`.
- `proxy.ts` protects `/conversations`, `/users`, `/room` (see i18n above); unauthenticated users go to `/<locale>`, the `(site)` route group with `AuthForm`.
- Socket connections are authenticated in `server/socket.ts` by decoding the NextAuth session cookie with `getToken` (`token.email`, `token.sub` = user id). When the token's `exp` passes, the server closes the socket's transport (`scheduleExpiry`), so the client reconnects and is authenticated again with its current cookie.
- Server errors go through `logError(tag, error, context?)` (`app/libs/log.ts`): one JSON line per error in production, readable in dev; don't put secrets or message text in the context.

**Realtime (socket.io)**
- `server.ts` creates one HTTP server for Next and socket.io and awaits `initSocketServer` before listening; on SIGTERM / SIGINT it shuts down gracefully (`closeSocketServer`: sockets get a transport close, so clients reconnect on their own; then Redis and Prisma; forced exit after 8 s); `server/socket.ts` stores the io server on `globalThis.io`, which is how route handlers reach it (same process — no serverless/Vercel).
- Several instances: configure Redis (`REDIS_URL` or `REDIS_HOST`…) and the Redis adapter (`@socket.io/redis-adapter`) shares rooms, so emits from any instance reach every socket. Presence and call rooms are read with `io.fetchSockets()` / `io.in(room).fetchSockets()`, which ask the whole cluster — don't reintroduce in-memory counters. If Redis is unreachable at boot the server exits after 10 s. Long-polling across instances needs sticky sessions at the load balancer.
- Client: one shared socket from `getSocket()` (`app/libs/socket-client.ts`). It is connected by `useActiveChannel` (mounted via `ActiveStatus` in the root layout) once the session is authenticated.
- Rooms (`app/libs/socket-rooms.ts`): `user:<email>` (joined automatically on connect), `conversation:<id>` (client calls `subscribeConversation`, server checks membership), `call:<roomId>`.
- Events — conversation room: `messages:new`, `messages:update` (bound in `conversations/[conversationId]/components/Body.tsx`). User room: `conversation:new`, `conversation:update`, `conversation:remove` (bound in `conversations/components/ConversationList.tsx`), `call:incoming` / `call:declined` (bound in `app/components/IncomingCall.tsx`, mounted in the `[locale]` layout so it rings on every page except the call screen; it renders `IncomingCallModal`). A `conversation:update` that carries `lastMessageAt` (new message) moves that conversation to the top; one without it (seen) updates in place.
- Presence: `presence:online` is sent on every connection (clients add idempotently, so concurrent tabs can't race) and `presence:offline` once `fetchSockets` finds no socket left for that user; `presence:list` on connect. They carry emails into the zustand store `useActiveList`; components read it through `useIsActive(email)` so only the affected avatar re-renders.

**Video calls**
- Audio or video: the call message carries `callType` (`audio` | `video`; missing on older calls = video), set from the phone / camera buttons in the conversation `Header.tsx` and sent along with `call:incoming` (also when re-sent on reconnect). The room page reads it back from the conversation's latest call message (`app/actions/getCallType.ts`), so both peers agree, and passes `audioOnly` to `Room.tsx`: it starts with no camera (avatar + status / timer, self-view hidden but mounted: the handlers use its ref). Every call negotiates a video transceiver (the host adds an empty `sendrecv` one when it has no camera track; the answerer flips a `recvonly` one to `sendrecv`), so the camera button switches between audio and video in any call with `replaceTrack`, never a new offer / answer: off stops the camera track and sends `null`, on grabs a new one. Remote tracks are collected into `remoteStream` from `ontrack` (an empty transceiver has no stream). The other side learns camera on / off from `call:media`. Call strings take `kind` in an ICU `select` (`{kind, select, audio {...} other {...}}`).
- Starting a call (`app/[locale]/conversations/[conversationId]/components/Header.tsx`) posts a message with `isCall: true` to `/api/messages` (and only enters the room once that succeeded), which also emits `call:incoming` to the other participants. That emit is one-off, so on every socket connection the server re-sends the calls still ringing for that user (`resendRingingCalls`: a call message from someone else within `CALL_RING_TIMEOUT_MS` whose call room holds only the caller); a callee whose socket was down at that moment, or who opens the app while it rings, still gets it. Accepting navigates to `/room/<conversationId>` (room id == conversation id).
- `call:join` (with ack) admits at most 2 conversation members and picks the host: the socket stamps itself (strictly increasing `nextJoinStamp`, not raw `Date.now()` — ties made both peers host), joins and snapshots the room in one synchronous step, then ranks peers by stamp. Keep those three steps free of `await`. Without Redis that rank also picks the host (exact in one process). With Redis the stamps only admit peers (instances' clocks differ) and `claimCallHost` picks the host: the socket id stored in `call-host:<roomId>` (Lua claim-if-empty; a holder no longer in the room is replaced by compare-and-swap; 24 h TTL only cleans up). Roles are fixed at join: when one peer leaves, the other leaves too (`Room.tsx`), so no handover is needed. Signalling events `call:ready`, `call:offer`, `call:answer`, `call:ice-candidate` and `call:media` (`{ mic, camera }`, shown as muted / camera off on the other side; validate it, it is relayed unchecked) are relayed as-is to the other peer (`CALL_SIGNALS`); `call:leave` or a disconnect sends `call:peer-left`.
- Declining (`IncomingCallModal`) emits `call:decline`; the server checks membership and sends `call:declined` `{ roomId, by }` to the user rooms of every member for a 1:1 conversation (the caller's `Room.tsx` leaves with a toast, only while still `waiting`; the callee's other tabs stop ringing), and only to the decliner's own tabs for a group. Nobody answering: after `CALL_RING_TIMEOUT_MS` (`app/libs/call.ts`, shared by both sides) the callee's modal closes and the caller, still `waiting`, leaves with a "no answer" toast. A caller leaving while still `waiting` (hang-up button or no answer) first emits `call:cancel`; the server accepts it only from a socket in that call room and sends `call:cancelled` `{ roomId, by }` to the other members' user rooms, where `IncomingCall` stops ringing. The server also sends `call:cancelled` itself whenever the last peer leaves a call room (`call:leave` or a disconnect: tab closed, Back, network lost), so a caller who leaves without `call:cancel` still stops the ringing; after an answered call it is a no-op. Ring / ringback tones are synthesized by `useCallTone` (Web Audio, no files).
- Call log: the call message carries `callStatus` (`CallStatus` enum), `callAnsweredAt`, `callEndedAt`. `/api/messages` creates it `ringing`; only the socket server moves it, through `moveCall` in `server/call-log.ts`: `ringing → answered` when a second peer of another user joins (`call:join`; the caller's own second tab doesn't count), `answered → ended` when either peer leaves, `ringing → declined` on a 1:1 `call:decline` (written before `call:declined` goes out, so the caller's leave that follows can't log it missed), `ringing → missed` on `call:cancel` or when the last peer leaves while it rings. Each move is an `updateMany` on id + expected status, so racing events never move a call back. A move emits `messages:update` (chat) and, when the call is still the last message, `conversation:update` without `lastMessageAt`. `MessageBox` / `ConversationBox` render it (declined, missed, or the duration via `callDurationSeconds` / `formatCallDuration` in `app/libs/call.ts`); calls from before these fields show the direction only.
- `app/[locale]/room/[roomId]/components/Room.tsx` does peer-to-peer WebRTC. Its socket listeners are registered once per room and call the latest handlers through `handlersRef` (filled in a `useLayoutEffect`), so the effect depends on `roomId` only — don't add the handlers to its deps.
- ICE servers come from `getIceServers(userId)` (`app/libs/ice-servers.ts`), passed in by the room page: STUN, plus TURN when `TURN_URLS` and `TURN_SECRET` are set, with short-lived credentials in coturn's `use-auth-secret` scheme (no static TURN password in the browser).

**Uploads (S3)**
- `ImageUploadButton` → `uploadImage` (`app/libs/upload.ts`) asks `POST /api/uploads` for a presigned PUT URL plus the headers to send (`app/libs/s3.ts`), uploads straight from the browser, and stores the returned public URL (message `image` or user `image`).
- Content type, length and the tag `status=pending` are signed into the URL (`x-amz-tagging` is kept a header via `unhoistableHeaders`; in the query string S3 ignores it). Allowed types and the 10MB limit live in `app/libs/upload.ts`. Keys are `uploads/<userId>/<uuid>.<ext>`.
- Before saving a message image or avatar, routes call `markUploadsUsed` (removes the pending tag; fails, and the route returns 400, if the object doesn't exist). A bucket lifecycle rule expiring objects tagged `status=pending` removes uploads that were never used.
- `/api/messages` and `/api/settings` only accept the caller's own uploads: `isUploadedFileUrl(url, userId)` matches the exact key format and the owner id in it. Settings also keeps the user's existing image (e.g. an OAuth avatar).
- Cleanup: `cleanUpUploads(urls)` (`app/libs/upload-cleanup.ts`) deletes S3 objects that no user avatar or message image references any more; it runs in the background after a replaced avatar or a deleted conversation.
- The bucket must allow public `GetObject` on `uploads/*` (or sit behind CloudFront via `NEXT_PUBLIC_S3_PUBLIC_URL`) and have CORS allowing `PUT` from the app origin.
- `images.remotePatterns` in `next.config.js` allows only this app's upload host (`NEXT_PUBLIC_S3_PUBLIC_URL`, else `<bucket>.s3.<region>.amazonaws.com`, read at build time) plus the GitHub and Google avatar hosts. Any other image host makes `next/image` throw, so new image sources must be added there.
